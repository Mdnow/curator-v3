## 1. AI / OpenRouter

### 1.1. Free-модели постоянно возвращают 429 (главная боль)

**Проблема.** Категории заметок не заполнялись, чат отвечал «AI временно недоступен. Попробуй через минуту».

**Причина (две, и обе были важны):**

1. **Невалидный `OPENROUTER_API_KEY` на Railway.** Строка ключа в Railway-окружении была устаревшей (72 симв., `401 User not found` при прямом запросе к OpenRouter). Локальный ключ в `.env` (73 симв.) работал. Из-за этого прод **вообще не мог ходить в AI** — упали и категории, и чат. Диагностика: вытащили ключ Railway через `railway variables --json`, сравнили с локальным, прогнали напрямую против OpenRouter — все три тестовые модели вернули 401.

2. **Узкая ротация моделей.** В v3 было только 3 free-модели, из которых `google/gemma-4-31b-it:free` стабильно в 429. v2 решал это широкой ротацией из 7 моделей — v3 её случайно зарезали.

**Решение.**

- Обновили ключ: `railway variables --set "OPENROUTER_API_KEY=$key"` (значение из локального `.env`) + редеплой.
- Расширили `FREE_MODELS` до 6 моделей, проверенных вживую:
  - `nvidia/nemotron-3-super-120b-a12b:free` — работает
  - `google/gemma-4-26b-a4b-it:free` — работает
  - `nvidia/nemotron-3-ultra-550b-a55b:free` — работает
  - `nvidia/nemotron-3-nano-30b-a3b:free` — работает
  - `google/gemma-4-31b-it:free` — в 429, оставлен как fallback
  - `openai/gpt-oss-20b:free` — возвращает 200 с пустым `content` (учтено guard-ом)
- Убрали мёртвые: `poolside/laguna-m.1:free` → **404 No endpoints found**, `openrouter/free` → 200 с пустым `content`.
- Сделали **двойной проход** по списку (2 раунда по всем моделям) — на случай кратковременных 429.
- Добавили **guard на пустой контент**: раньше `content=None` возвращался как успех, из-за чего чат мог получить `None` и упасть в `re.search`.

**Ключевой вывод.** Прежде чем винить модели — проверь ключ. Один невалидный ключ на проде отключает весь AI-функционал, а ошибка выглядит как «free-модели отвалились».

### 1.2. Модель возвращает обрезанный JSON → fallback «без категории»

**Проблема.** `analyze_note` иногда возвращал пустую категорию, хотя `call_ai` отвечал успешно. Сырой ответ обрывался на середине JSON: `{"summary": "...", "category": "Наблюдения", "sentiment` — без закрывающих скобок. `json.loads` падал, и функция отдавала fallback.

**Причина.** У free-моделей качество генерации нестабильно: некоторые завершают ответ раньше конца JSON. Плюс старая логика `call_ai` возвращала **первый** ответ с HTTP 200, даже если JSON был битый — хорошие модели не получали шанса.

**Решение.** Ввёл `call_ai_json()` — парсит ответ каждой модели и пробует следующую, пока не получит валидный JSON:
- `_request_model(client, model, ...)` — единый вызов с обработкой 429/ошибок/пустого контента.
- `_parse_json_content()` — срезает markdown-обёртки ``` ``` ````, парсит JSON, принимает только `dict`.
- `call_ai_json()` — 2 прохода по всем моделям, возвращает первый валидный JSON.
- `analyze_note`, `analyze_dream`, `daily_patterns`, `thread_suggest` переведены на `call_ai_json`.

**Результат.** Локально и на проде категория стабильно определяется («Саморазвитие», «Задачи» и т.п.), summary/sentiment/keyphrases заполняются.

### 1.3. Двойное экранирование `{{ }}` в промптах

**Проблема.** `DAILY_PATTERNS_PROMPT` и `THREAD_SUGGEST_PROMPT` содержат JSON в теле промпта и вызываются через `.format()`. Фигурные скобки `{` в JSON уходили в `.format()` как шаблон → `KeyError` / мусор.

**Решение.** Экранировать: `{{ }}` вместо `{ }` в местах, где вызывается `.format()`.

### 1.4. Таймауты

**Проблема.** При полном отказе всех моделей запрос мог висеть до 3 минут (6 моделей × 15с × 2 прохода), и фронт уходил в «ошибка соединения».

**Решение.** Пока принято как есть: рабочие модели отвечают быстро, 429 приходят мгновенно. Таймаут `httpx.AsyncClient(timeout=15)` на один вызов. Дальнейшее усиление — через freellmpool (см. §1.6).

### 1.5. Урок по ротации free-моделей

- Каталог free-моделей OpenRouter меняется: модель может исчезнуть (404) или уйти в перманентный 429.
- Перед фиксацией списка — тестировать каждую модель отдельно, коротким таймаутом (одна «зависающая» модель блокировала весь пакетный тест).
- Ротация должна быть **широкой и парсить JSON**, а не просто брать первый 200.
- Список актуальных free-моделей можно получить: `GET /api/v1/models` с заголовком `Authorization: Bearer $key`, фильтр `id like "*:free"`. На момент теста — 14 моделей.

### 1.6. Планы: freellmpool (не внедрено)

**Проблема.** Одиночный пул free-моделей OpenRouter всё равно хрупкий (429, суточные лимиты).

**Идея.** `0xzr/freellmpool` — пул free-тиров 24 провайдеров (Groq, Cerebras, Gemini, NVIDIA, OpenRouter, keyless-провайдеры Pollinations/OVHcloud/Kilo и др.) за одним OpenAI-совместимым endpoint с авто-failover и квотой на день. Даёт resilience там, где текущая ротация одного провайдера упирается в лимит.

**Статус (решение от 06.08.2026).** Зафиксировано как рекомендация, **внедрять не стали**: корневая причина 429 устранена валидным ключом + ротацией из 6 free-моделей, рабочее поведение подтверждено на проде. Если снова упрёмся в лимиты — первым шагом расширить `FREE_MODELS` из каталога `/api/v1/models`, вторым — внедрить `0xzr/freellmpool` (Python-библиотекой внутрь backend, либо отдельным Railway-сервисом-proxy).

## 2. Кодировки / кракозябры

### 2.1. Кракозябры в тестах (НЕ баг приложения)

**Проблема.** Ответы API выглядели как `�۶� �������㯥�` или `РљСѓСЂР°С‚РѕСЂ`, хотя сайт работал.

**Причина.** Это была **консоль/инструменты**, не приложение:
- PowerShell 5.1 и окно bash-тула неправильно декодируют UTF-8 в кириллице.
- Сырые байты были валидным UTF-8 (проверено hex: `D0 B2 D1 80...` = «вре...»).

**Решение (рабочий паттерн для проверок):**
- Не смотреть на ответ в консоли. Писать через `curl.exe -o file.json` (сырые байты) и читать файл инструментом `Read` или скриптом Python с записью в файл.
- **Никогда** `Out-File -Encoding ascii` для кириллицы — заменяет все не-ASCII на `?` и портит данные (дважды наступали на это при диагностике).
- `Out-File -Encoding utf8` в PS 5.1 пишет UTF-8 **с BOM** — если тело JSON уходит в запрос, BOM попадает в строку (портит префикс сообщения).
- Для POST-тела JSON: писать файл и слать `curl.exe --data-binary @file`, а не экранировать JSON в кавычках (в PS 5.1 экранирование ломается).

### 2.2. Приложение само по себе с кодировкой в порядке

- FastAPI отдаёт UTF-8 корректно; сырые байты ответа валидны.
- Фронт экранирует через `esc()` и innerHTML-безопасно; в базе текст хранится в UTF-8.
- Favicon отсутствует → 404 в консоли браузера, на работу не влияет.

### 2.3. Двойная кодировка в закоммиченном `index.html` (кракозябры на проде)

**Проблема.** Весь статический текст UI на проде показывался кракозябрами: title браузера `РљРЈР РђРўРћР v3`, кнопки `Р—Р°РјРµС‚РєРё`, `РЎРѕРЅ` и т.п. При этом JS-рендер (app.js) был чистым. Был период, когда часть фронта правилась PowerShell `Set-Content` с неверной кодировкой — файл уехал в git в «двойном» виде (UTF-8 прочитан как однобайтовая кодировка и пересохранён).

**Как проявилось и что проверили.**
- `git diff` показал всю кириллицу как замену мозаики на правильные символы.
- Проверка байтов через Python (UTF-8 decode всего файла) — рабочий файл валиден, BOM нет.
- Симптом из браузера (title с мозаикой) — признак, что **задеплоен был именно битый файл**, т.е. проблема была в репозитории, а не в отображении.

**Решение.** Пересохранить `index.html` в валидном UTF-8 (случайно сделано той же `Set-Content` при поднятии `?v=5 → ?v=6`). После деплоя title и весь статический текст — корректный русский.

**Уроки.**
- Фронтенд-файлы с кириллицей править только инструментом `edit`/`write` (UTF-8), не PowerShell `Set-Content`.
- Контроль: быстрый скрипт `check_mojibake.py` — просканировать все `.html/.js/.css` на мозаичные маркеры (`Р·Р°РјРµС‚РєРё`, `РЎРѕРЅ` и т.п.).
- Проверка «на проде»: смотреть title вкладки в браузере — мозаика там = битый файл в репо, а не консоль.

## 3. Railway-деплой

### 3.1. Пуш в GitHub НЕ деплоит на Railway

**Проблема.** Казалось, что после `git push` всё само задеплоится. Оказалось — последний успешный деплой был недельной давности, все мои фиксы не доезжали.

**Причина.** Сервис не привязан к GitHub-источнику (собирается из загруженного кода, не из репозитория).

**Решение.** Деплой вручную через Railway CLI:
```
railway up --detach        # собрать из локальной папки и задеплоить
railway redeploy --yes     # пересобрать текущий деплой
railway deployment list    # статус (SUCCESS / DEPLOYING / FAILED / REMOVED)
```
Для диагностики деплоя `railway deployment logs` НЕ существует — используется `railway logs` (рантайм-логи контейнера).

### 3.2. Окружение Railway

- Токен CLI лежит в `~/.railway/config.json` (`accessToken`) — Railway CLI доступен без доп. настройки.
- Переменные: `railway variables` (таблицей), `railway variables --json` (машинно-читаемо), `railway variables --set "K=V"`.
- `--set` переменной может триггерить автодеплой; иногда создаёт два деплоя подряд. Перепроверять `deployment list`.
- **Секреты НЕ должны попадать в репозиторий**: `.env` в `.gitignore`. Для загрузки на Railway добавили `.railwayignore` (исключает `.env`, скриншоты, тест-файлы), т.к. `Dockerfile` делает `COPY . .`.

### 3.3. Несколько деплоев подряд

**Проблема.** Ручной деплой + автодеплой от смены переменной дали параллельные деплои, один ушёл в FAILED.

**Решение.** Не страшно: Railway держит последний SUCCESS как активный. Ориентироваться на `deployment list`, ждать статуса именно нужного ID.

## 4. Фоновые задачи и БД

### 4.1. AI-вызовы внутри блокировки пула БД

**Проблема.** `_analyze_in_background` (notes), `_analyze_dream_in_background`/`dream_insight_endpoint`/`dream_patterns` (dreams), `daily_insight` (insights) делали AI-запросы (до 45-180с!) **внутри** `pool.acquire()` / `get_db()` — держали соединение с БД, пока AI думает. Это исчерпывало пул и вешало сервис.

**Решение.** Вынести все AI-вызовы из контекста соединения: сначала `await analyze_*(...)`, затем отдельно `await pool.acquire()` для записи результата.

### 4.2. Единый паттерн доступа

- Чтение: `async with get_db() as db:` (выдаёт соединение из пула).
- Фоновые задачи: брать пул через `from backend.db import get_pool`, `pool.acquire()`, закрывать после записи.
- Никогда не держать соединение во время сетевых вызовов к OpenRouter.

## 5. Чат и сессии (задача «архив — бардак»)

### 5.1. История «перемешана» между диалогами

**Проблема.** Сессии были временны́ми корзинами (новая через 2ч после последнего сообщения), но контекст для AI брался из **последних 40 сообщений всех времён** — диалоги смешивались. Архив был отдельной read-only панелью без возможности продолжить диалог.

**Решение.**
- Backend: `POST /ai/chat` принимает опциональный `session_id`. Если передан и принадлежит пользователю — продолжаем эту сессию; история для контекста фильтруется по сессии.
- Новый диалог: фронт шлёт `session_id: null`, backend решает (новая при разрыве >2ч, иначе продолжение последней).
- `DELETE /chat/sessions/{id}` — удаление диалога; `/chat/history` — очистка всех.
- Frontend: топбар чата «куратор» + кнопки `✚` (новый диалог) и `☰` (диалоги). Список диалогов: дата, превью (первое сообщение = название), счётчик сообщений, кнопка удаления `✕`, поиск, «очистить всё». Клик по диалогу — закрывает панель и **загружает переписку прямо в окно чата**, `currentSessionId` запоминается, отправка продолжает этот диалог.

### 5.2. Куратор не видел паттерны

**Проблема.** Контекст чата = последние 30 заметок + избранное. Пользователь просил: куратор должен видеть связи и паттерны мыслей.

**Решение.** В system-промпт добавлены без AI-вызова (правильно дёшево):
- `СВОДКА ТЕМ` — подсчёт AI-категорий за последние заметки (без «без категории»), топ-4.
- `ПОСЛЕДНИЕ ЗАПИСИ О СНАХ` — последние 5 расшифрованных снов.
- Избранные мысли как фокус (было).
Проверено на проде: куратор ответил со ссылкой на «свободу и дышащую среду» из реальных заметок.

## 6. Frontend

### 6.1. Кэш браузера душит новые версии

**Проблема.** CSS/JS меняются, браузер кэширует старые файлы.

**Решение.** Cache-busting query: `?v=4` → `?v=5` → `?v=6` во всех `<link>`/`<script>` в `index.html` при каждом выпуске фронтенда.

### 6.2. Эмодзи в UI

**Правило пользователя:** никаких эмодзи. Заменены на текст/геометрические глифы: `≡`, `✎`, `☐`, `☽`, `◇`, `✦`, `↓`, `•`, `mic`. При новом коде проверять, что не затесался эмодзи (находили `📕` в кнопке архива → заменён на `☰`).

### 6.3. `isMobile()` была константой

**Проблема.** `isMobile()` был константой, вычисленной один раз — ресайз не пересчитывал мобильный режим.

**Решение.** Сделать `isMobile()` функцией (проверка ширины на каждый вызов).

### 6.4. Мобильный чат

- Чат на мобильном полноэкранный: скрыт header и bottom bar, добавлена кнопка «назад» (`←`).
- Панель диалогов — внутри чат-секции, работает и на десктопе, и на мобильном.

### 6.5. Переанализ старых заметок «без категории»

**Проблема.** Заметки, созданные в сломанный период, навсегда висят с `ai_category='без категории'` (fallback от невалидного ключа записался в БД).

**Решение.**
- Backend: `POST /api/notes/reanalyze` — выбирает до 200 заметок пользователя с `ai_category IS NULL/''/'без категории'`, планирует `_reanalyze_in_background` (тот же код, что и `_analyze_in_background`, но без thread-матчинга — только AI-поля).
- Frontend: кнопка «переанализ» в сайдбаре (десктоп) и в drawer «инструменты» (мобайл); тост с числом запущенных.
- Безопасно: меняются только `ai_summary/ai_category/ai_sentiment/ai_keyphrases`; `content_encrypted` не трогается.

**Реальность прогона.** 176 заметок, ~30с на заметку (ротация через 429 и пустые ответы) — фоновый прогон занимает ~1.5-2ч. Токен/процесс переживает это спокойно; чекпоинты каждые 10/25 заметок в лог. Для больших объёмов — учитывать это время либо расширять `FREE_MODELS`.

**Goals-ревью пересборки (ADR-0008, 10.08).** Найдено и исправлено в `backend/routes/goals.py` + `backend/ai.py` + `frontend/js/app.js`, коммит `6c57ad5`:
- **Галлюцинированные `note_id`** (цифры, которых нет в `date_map`) теперь отфильтровываются; цель, у которой после фильтра осталось меньше **двух** подтверждений, не проходит в созвездие (раньше в evidence могли попасть несуществующие ссылки).
- **Дедуп дублей `existing_goal_id`**: если AI вернул одну цель дважды (или `existing_goal_id` продублирован) — второй раз цель не затирается, первый «chosen» остаётся. Раньше повторный UPDATE перетирал evidence первого.
- **`existing_goal_id=true/false` из AI** (логический тип вместо числа) теперь игнорируется и в AI-слое (`ai.py`), и в rebuild — раньше `True` мог попасть в `by_id` как ключ 1.
- **`WHERE id=$1 AND user_id=$2`** добавлен в оба UPDATE (существующая цель → active, активная → archived) — защита от cross-user при невалидном id.
- **Вся пересборка в одной транзакции** (`db.transaction()`): при сбое посередине не останется полусостояния активные/архив.
- **UX**: индикатор «пересобираю созвездие» живёт до 90с, polling каждые 4с (раньше статус скрывался сразу после POST, а 3 перезагрузки в первые 8с могли показать ещё старые данные).
- Verifier: `py_compile` + `ruff` (новых ошибок нет, остались только legacy I001/BLE001/S112) + `node --check` — OK. Деплой `4b12b553` SUCCESS, прод health 200, логи `Application startup complete`.

## 10. QA-прогон 06.08.2026 (live-API, ASGI-транспорт)

Прогон без поднятия сервера: `httpx.ASGITransport(app=app)` in-process. Пользователи `qa_u1`/`qa_u2`, контекст по-русски.

**Покрыто (40+ проверок, до фиксов):** auth (duplicate→400, wrong password→401, no/bad token→401), CRUD заметок/задач/снов, избранное (note+task), даты, пагинация, чат (send/resume/history/sessions/search/save-thought), инсайты, паттерны, бэкап, health.

**Результаты:**
- **IDOR-изоляция работает**: все попытки юзера B менять/читать данные юзера A → 404/пусто; `DELETE`/`UPDATE` чужого → no-op. Данные не потекли.
- XSS-пайлоады в контенте заметок проходят round-trip без потерь (на фронте экранируются `esc()`).
- Крах всего один: `GET /api/notes?page=0` → `asyncpg InvalidRowCountInResultOffsetClauseError: OFFSET must not be negative` → 500.

### 1.7. Дневной лимит free-моделей: 50 запросов/день (главный ограничитель)

**Проблема.** «AI снова недоступен» после фонового переанализа. Все 6 free-моделей в 429, включая ранее рабочие.

**Причина.** OpenRouter free-тариф без кредитов = **50 запросов free-моделей в сутки на ключ**. Ответ 429:
```
Rate limit exceeded: free-models-per-day. Add 10 credits to unlock 1000 free model requests per day
```
Заголовок `X-RateLimit-Reset` (Unix ms) = следующий полуночный сброс по UTC. Фоновый переанализ 125 заметок + live-тесты сожгли лимит за ~1.5 часа. При этом `analyze_note` при 429 молча возвращал «без категории» — выглядело как поломка, а не лимит.

**Диагностика.**
- Прямой запрос к `https://openrouter.ai/api/v1/chat/completions` → 429 с текстом лимита (curl, т.к. PS 5.1 не умеет `-SkipHttpErrorCheck`).
- `GET /api/v1/key` — ключ валиден, `is_free_tier: true`, `usage: 0` (free-запросы не считаются в usage).

**Решение (3 фикса + рекомендация).**
1. **Остановлен фоновый переанализ** (PID 32) — не жечь лимит. Заметки без категории переберутся кнопкой «переанализ» после сброса.
2. **`ai.py`**: глобал `AI_LAST_ERROR` — при 429 сохраняет текст ошибки; `chat_with_context` при лимите отвечает понятно («Бесплатный лимит... добавь $10 → 1000/день»), `analyze_note` кладёт это в `error`.
3. **`notes.py`**: `_analyze_in_background` и `_reanalyze_in_background` теперь пропускают запись при `ai.get("error")`. Раньше фолбэк `category='без категории'` (truthy) проходил условие `ai.get("summary") or ai.get("category")` и затирал поля пустыми значениями.
4. **Рекомендация (главное)**: добавить $10 на openrouter.ai → лимит free-запросов поднимается до **1000/день**. Без этого 50/день не хватит даже на обычный день (заметки + чат + инсайты + сны). Проверка лимита: заголовок `X-RateLimit-Remaining`/`X-RateLimit-Reset` в 429.

### 1.8. Чистые HTTP-коды от OpenRouter (диагностика)

| Код | Значение | Что делать |
|---|---|---|
| 401 | `User not found` — невалидный ключ | обновить `OPENROUTER_API_KEY` на Railway |
| 404 | `No endpoints found` — модель снята с free | убрать из `FREE_MODELS` |
| 429 | `free-models-per-day` — дневной лимит free | ждать сброса (00:00 UTC) или пополнить $10 → 1000/день |

... WHERE content LIKE $2 ESCAPE '\\'

**Проверено.** q=`50%` → 1 результат (только точное совпадение), q=`50` → 2 (user+assistant), q=`a_b` → только реальные.

## 13. Сессия 07.08.2026 — «Карта дня» (когнитивная карта мышления)

## 15. Сессия 08.08.2026 — AI-провайдер → OpenCode Zen (бесплатные free-модели)

Замена OpenRouter на OpenCode Zen как основного провайдера. Причина: у OpenRouter лимит 50 запросов/день на free-ключ → постоянные 429; у Zen есть бесплатные модели без этого ограничения.

### 15.1. Открытие: big-pickle — это Zen-модель

Модель `opencode/big-pickle`, которой пользователь пользуется в opencode, — это **бесплатная модель OpenCode Zen**. В доке `/docs/zen` их 8 (все Free):

| Модель Zen | Model ID (в API) |
|---|---|
| Big Pickle | `big-pickle` |
| DeepSeek V4 Flash Free | `deepseek-v4-flash-free` |
| MiMo-V2.5 Free | `mimo-v2.5-free` |
| Nemotron 3 Ultra Free | `nemotron-3-ultra-free` |
| Laguna S 2.1 Free | `laguna-s-2.1-free` |
| Ling-3.0-tiny Free | `ling-3.0-tiny-free` |
| LongCat-2.0 Free | `longcat-2.0-free` |
| North Mini Code Free | `north-mini-code-free` |

Эндпоинт OpenAI-совместимый: `https://opencode.ai/zen/v1/chat/completions` (`@ai-sdk/openai-compatible`). В конфиге opencode id имеет вид `opencode/<model-id>`, но в сыром API `model` = просто `<model-id>`. Ключ — OpenCode Zen API key (opencode.ai/auth).

### 15.2. Архитектура: провайдер-слой в ai.py

Раньше `call_ai`/`call_ai_json` были захардкожены на OpenRouter (URL+ключ+модели из `FREE_MODELS`). Теперь:

- `PROVIDERS` — список словарей `{name, url, key, models, extra}`. **Zen первым**, OpenRouter fallback. `extra` — доп. поля тела запроса (для OpenRouter `reasoning: {exclude: true}`).
- `_request_model(client, provider, model, ...)` — единый вызов с обработкой 429/ошибок/пустого контента, строит тело из `provider["extra"]`.
- `call_ai`/`call_ai_json`/`chat_with_context` — 2 прохода по провайдерам, внутри по моделям; возврат первого успеха.
- Guard `if not PROVIDERS:` заменил `if not OPENROUTER_API_KEY:` во всех анализаторах.
- `embed_text()` остался на OpenRouter (`nvidia/nemotron-3-embed-1b:free`) — у Zen бесплатных эмбеддингов нет.

`backend/config.py`: `ZEN_API_KEY` (из `.env`), `ZEN_URL`.

### 15.3. Грабли с Zen-моделями (важно)

1. **`big-pickle` и `deepseek-v4-flash-free` — reasoning-модели**: ответ приходит с `reasoning_content` (размышления на английском) + `content` (финальный JSON). Мы читаем только `content` — ок.
2. **`max_tokens` считается ВМЕСТЕ с reasoning-токенами**. big-pickle на простой JSON съела 471 из 500 токенов (311 reasoning у deepseek). Старые лимиты (`thread_suggest` 200, `day_essence` 300) обрезали бы ответ до пустоты → подняты (см. 15.4).
3. **Латентность**: простой JSON-запрос ~11с (против ~3с у старых free). Таймаут httpx поднят 15с→90с, иначе каскад 2×8 попыток × 15с сжигал весь бюджет.
4. **Приватность**: у free-моделей Zen (big-pickle в т.ч.) «данные могут использоваться для улучшения модели». Куратор шлёт личные мысли/сны открытым текстом — это осознанное решение пользователя для личного использования.
5. **Free-модели Zen «на ограниченное время»** — могут исчезнуть. Для этого и оставлен fallback на OpenRouter.
6. **Rate-limit в сообщениях** нейтрализован: больше не пишем «лимит OpenRouter 50/день».

У ruff 0.16 в дефолте много правил — голый `ruff check` даёт 112 замечаний (I001/UP045/BLE001/S110/DTZ...), почти всё legacy. Чтобы кнопка была честной (не «НЕ ГОТОВО» из-за старых стилистических замечаний), в проекте создан `ruff.toml`: `select = ["F", "E9"]` — только реальные баги (неопределённые имена, неиспользуемые импорты) и синтаксис.

В PostgreSQL `date - interval` → `timestamp`; сравнение `timestamp >= date` в `$2::text` — asyncpg неявно типизировал параметр как `interval` (из-за `- INTERVAL` в том же выражении) → `DataError: invalid value for interval` (toordinal).

Исправление (`backend/routes/dreams.py`):
- `CURRENT_DATE::text` → `CURRENT_DATE`;
- `note_date >= $2::text - INTERVAL` → `note_date::date >= $2::date - INTERVAL '7 days'`.

## 21. 11.08.2026 — Устойчивость пула к обрывам Neon: health-check + retry в `backend/db.py`

### 21.1. Задача
Повторяющиеся разрывы соединения с Neon (`ConnectionDoesNotExistError: connection was closed in the middle of operation`, WinError 1225) на нестабильной сети пользователя. Вопрос: есть ли бесплатная альтернатива Neon.

### 21.2. Решение
Альтернатив **бесплатных** нет (Railway Postgres — разовый $5 credit; Supabase паузится после 7 дней idle; Aiven/Render Postgres — платные). Остаёмся на Neon, но убираем чувствительность к обрывам на уровне пула (`backend/db.py`):

- **Health-check при acquire**: `_healthy_connection()` берёт коннект, проверяет `SELECT 1`, мёртвый отбрасывает; до 4 попыток с exponential backoff (`0.2 * 2^attempt`).
- **`max_inactive_connection_lifetime=30.0`**: пул сам выбрасывает протухшие idle-коннекты (Neon гасит compute после ~5 мин простоя и рвёт их).
- **Retry на разрывы**: `_RETRYABLE` (`ConnectionDoesNotExistError`, `InterfaceError`, `ConnectionResetError`, `OSError`) — на эти ошибки соединение безопасно перебрать.
- `min_size=2 → 1`: не держать лишних долгоживущих коннектов к серверлесс-БД.

Правка попала в коммит `e044519` (11.08 11:19) вместе с журналом 20-й секции; в журнале зафиксирована отдельно здесь.

### 21.3. Проверка
- `python -m py_compile backend/db.py` — OK.
- `ruff check backend/db.py` (select F/E9) — 0 замечаний.
- Интеграционный `test_feat.py` не гонялся: пишет в прод-Neon и жжёт AI-лимит; сеть нестабильна (§16.6, §20.8).

### 21.4. Замечания
- Health-check `SELECT 1` на каждый `get_db()` — небольшой оверхед (~1 раунд-трип), для масштаба приложения некритично.
- Если обрыв происходит посреди самой операции (не на acquire), спасёт только ретрай на уровне запроса — на будущее, если симптомы вернутся.

### 22.1. `test_feat.py` таймаутит на живом сервере: фоновые AI-задачи держат пул asyncpg

## 26. 14.08.2026 — Время в кураторе: перевод на московское (UTC+3)

### 26.1. Причина сдвига
Neon: `current_setting('TimeZone')` = `GMT`. Все колонки `created_at TIMESTAMP` (без time zone, db.py) хранят **naive-UTC** (значение `CURRENT_TIMESTAMP` = now() в GMT, при вставке в колонку без tz маркер теряется). Бэкенд отдаёт:
- notes.py:148, goals.py:37 — `str(r["created_at"])` → `"2026-08-14 05:42:47.567368"` (без tz-маркера);
- chat.py:221/322 — `r["created_at"]` (datetime) → FastAPI сериализует в `"2026-08-14T05:42:47.567368"` (тоже naive).

Фронт делал `new Date("2026-08-14 05:42:47")` — JS интерпретирует строку без tz как **локальное** время браузера. Для пользователя в Москве отображалось время UTC (на 3 часа раньше), в других локалях — произвольный сдвиг.

### 26.2. Решение (только фронт)
Единые функции в app.js:

## 28. 14.08.2026 — Баг модалки (блокировка входа) + адаптация под iPhone 12 Pro Max

### 28.1. Симптом
Пользователь не может войти: при открытии приложения на весь экран «пустое всплывающее окно», которое не закрывается. Клик по фону/кнопке не помогал.

### 28.2. Причина (важный урок про `hidden` и `display`)
Модалка `#noteModal` имеет атрибут `hidden`, но правило `.note-modal { display: flex }` (для центрирования карточки) имеет БОЛЬШУЮ специфичность, чем UA-стиль `[hidden] { display: none }` (специфичность 0,1,0 против 0,0,1 — и вообще UA-правила проигрывают авторским). Итог: модалка видна всегда (в т.ч. пустой экран входа), а `closeNoteModal()` ставит `hidden=true`, но CSS-ный `display:flex` не даёт скрыться.

**Фикс:** `.note-modal[hidden] { display: none; }` (специфичность 0,2,0 побеждает `.note-modal`).

**Правило на будущее:** если элементу задан `display` в CSS (flex/grid/block), атрибут `hidden` НЕ сработает. Либо использовать класс `.open`, либо всегда добавлять `[hidden] { display: none }` для таких элементов.

## 35. 17.08.2026 — Мгновенный отклик UI: optimistic-обновления и микро-анимации

### 35.1. Задача
Пользователь: «нажимаю на кнопки и не чувствую отклик — приходится ждать несколько секунд, пока выйдет сообщение либо об ошибке, либо об исполненном действии. Хочу отклик как в TikTok». Симптом: звёздочка избранного в целях загоралась только после ответа сервера + полной перерисовки списка.

Бэкенд при этом менять не нужно — все toggle-эндпоинты уже возвращают новое значение (`{"is_favorited": ...}`, `{"is_pinned": ...}`).

- `deleteNote`/`deleteTask`/`deleteGoal`/`archiveGoal`/`activateGoal`: карточка исчезает сразу, при ошибке — `loadX()` как fallback-откат.

**Микро-отклик кнопок** (CSS):

- `mobile.css`: hover-кнопки `.goal-archive`/`.goal-delete`/`.goal-activate`/`.task-delete` теперь `opacity: 1` на мобильных — раньше на тач-устройствах они были невидимы (показывались только при наведении мыши) и физически недоступны.

**Кэш-бастеры**: `app.js?v=23`, `base.css?v=7`, `animations.css?v=7`, `mobile.css?v=14` (правило §23.5).

## 36. 17.08.2026 — «Укутанная» механика: предсказуемый отклик кнопок (ADR-0015)

### 36.1. Задача
«Карта дня»: кнопки должны давать понятный результат, без непонятных состояний, без потери данных. Пользователь: «нажимаешь на кнопку и происходит непонятное состояние», «чат висит "думаю…"». Продолжение §35 (optimistic UI) — добить остальные кейсы «мёртвого» отклика.

### 36.2. Анализ (из кода)
Найдены зоны, где кнопка не отвечала или терялись данные:
- `api()` без таймаута — на медленном Render-проду висит молча до бесконечности.
- Чат: нет защиты от двойной отправки; `discussWithCurator`/`discussTheme` — гонка `setTimeout` с `sendChat` (могла отправлять дважды); `newChat()` без подтверждения.
- 401/сетевые ошибки: тост «ошибка» без причины или тихий выход в меню.
- Удаления/архив: карточка исчезала из DOM, даже если сервер вернул ошибку — данные «потеряны» на экране без объяснения.
- Пустые вкладки при первой загрузке: 2–4 сек «серый экран» без индикатора.
- Ввод в `#noteInput` терялся при перерисовке вкладки/смене даты.

### 36.3. Правила отклика (зафиксированы в ADR-0015)
1. Кнопка откликается мгновенно (состояние меняется по клику).
2. На время запроса — disabled + busy-индикатор (подпись «Думаю…», «Сохранение…»).
3. Введённое пользователем не теряется; причина сбоя объясняется понятным тостом.
4. Черновик заметки живёт в localStorage.
5. У всех запросов есть таймаут; на таймауте — явный тост «сервер не ответил, попробуй ещё раз».
6. Загрузка списков — скелетон-индикатор.
7. Удаление/архив — только после подтверждения сервера; иначе откат.
8. Новый диалог в чате — с подтверждением, если в текущем есть сообщения.

### 36.4. Решение (только фронт, коммит `be4f3ce`)
**`frontend/js/app.js`:**
- `api(method, path, body, opts)` на AbortController: `FETCH_TIMEOUT_MS=30000`, `CHAT_TIMEOUT_MS=90000`; 401 → `logout()` + toast «сессия истекла — войди заново»; `apiErrorMessage(e)` — человеческие формулировки (таймаут, сеть, сервер).
- `runBusy(btn, task, busyLabel)` / `setButtonsBusy(selector, busy)` — disable + смена подписи. Применено: «Пересобрать заметки», «Скачать бэкап», «Создать задачу».
- Черновик: `draftKey()='curator_draft_'+selectedDate`, `saveDraft`/`clearDraft`/`restoreDraft`; restore только если поле пустое; `clearDraft()` после успешного `saveNote`.
- Удаления/архив: класс `.deleting` (в CSS — opacity, pointer-events:none), карточка уходит из DOM после ответа; ошибка → `loadX()` как откат.
- `showListLoading(listSel)` — только если список пуст; применено в `loadNotes/loadTasks/loadGoals`.
- Чат: `if ($('#chatLoading')) return;` перед отправкой; `{timeoutMs: CHAT_TIMEOUT_MS}` в трёх местах `/ai/chat`; `newChat()` возвращает false при отмене confirm; `discussWithCurator/discussTheme/discussGoal/headsUp` — guard `if (!newChat()) return;` и вызов `sendChat()` напрямую, без `setTimeout`.
- `createTask`: флаг `taskCreating` + `runBusy` на `#taskFormSubmit`.
- Все голые `toast(e.message || 'ошибка')` → `toast(apiErrorMessage(e))`; `.catch(() => …)` → `.catch(err => …)`.

**CSS/HTML:**
- `base.css`: `button:disabled { cursor: default; opacity: 0.55; }`.
- `animations.css`: `.deleting` (opacity .45, pointer-events none), `.list-loading` (pulse).
- `index.html`: `app.js?v=24`, `base.css?v=8`, `animations.css?v=8`.

### 36.5. Проверка

## 37. 17.08.2026 — Ветки чата: диалог = тема с названием (ADR-0014)

### 37.1. Задача
Пользователь: «кнопки "обсудить" разбросаны по приложению, но их диалоги нигде не сохраняются, а архив главного чата — полный бардак без структуры. Хочу кнопки везде, но единый чат куратора и историю, по которой можно гулять и перечитывать». Избранная модель — ChatGPT/Claude: каждый вход («обсудить», «новый диалог») создаёт новую ветку с названием по смыслу.

### 37.2. Решения
1. **Модель веток**: отсутствие `thread_id` в запросе = новая ветка; наличие = продолжение той же. Проектный диалог (`project_id`, ADR-0013) остаётся отдельным путём — не мигрирует в ветки.
2. **Архив** — единый хронологический список веток (по последней активности): название + дата + число сообщений + поиск.
3. **Заголовок ветки** — AI по смыслу из первого сообщения, 2-5 слов, фоновая задача (BackgroundTasks), формат JSON через `call_ai_json` (как `ai_title` у заметок).

### 37.3. БД (`backend/db.py`)
```sql
CREATE TABLE IF NOT EXISTS chat_threads (
  id SERIAL PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title TEXT NOT NULL, created_at TIMESTAMPTZ DEFAULT now(), updated_at TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE chat_history ADD COLUMN IF NOT EXISTS thread_id INTEGER REFERENCES chat_threads(id) ON DELETE CASCADE;
```
Миграция в `init_db()`: группы `(user_id, session_id)` → ветки (заголовок — первые 60 символов первого сообщения; `updated_at` = последний `created_at`); сообщения с `session_id IS NULL AND project_id IS NULL` → ветка «старые сообщения»; «сироты» с `thread_id IS NULL AND session_id IS NULL` причисляются к ветке «старые сообщения»/своей ветке при существующем `thread_id`. Всё идемпотентно.

### 37.4. API (`backend/routes/chat.py`)
- `POST /api/ai/chat`: если `project_id` — старый путь; иначе `thread_id` из запроса; если нет — `INSERT chat_threads` + фоновая `_title_thread`; сообщение пишется в `chat_history` с `thread_id`; после ответа — `UPDATE chat_threads SET updated_at`. Ответ: `{..., "thread_id": N, "session_id": N}` (session_id оставлен для совместимости фронта).
- `GET /chat/threads` — список веток: `title` (fallback — превью последнего сообщения), `started/ended`, `msg_count`. Новые ветки без заголовка в начале списка.

- `GET /chat/search` — теперь возвращает `thread_id` для открытия ветки.

## 38. 17.08.2026 — Загрузка файлов в чат Куратора (ADR-0016)

### 38.1. Задача
Задача из «Карты дня»: чат Куратора принимает только текст, нет канала передачи контекста документов. Подшаги: схема приёма и типы файлов → извлечение текста и передача модели → сохранение осмысленного результата в историю чата.

### 38.2. Схема приёма
`POST /api/chat/upload` (multipart/form-data): `file` (обязательно), `message` (необязательно), `thread_id` (необязательно, без него — новая ветка). Типы по расширению: текст `.txt/.md/.markdown/.csv/.json/.log`, `.pdf`, изображения `.png/.jpg/.jpeg/.webp/.gif`. Лимит 5 МБ, извлечённый текст до 20 000 символов (как у заметки), избыток обрезается с пометкой.

### 38.3. Извлечение (`backend/fileparse.py`)
- Текст: попытка `utf-8` → `cp1251` → `latin-1`, иначе `replace`.
- PDF: `pypdf.PdfReader`, постраничный `extract_text()`, ошибки оборачиваются в честное сообщение.
- Изображения: не парсятся локально — `describe_image()` в `ai.py` (vision).
- Пустой результат → `FileParseError` → 422.

### 38.4. Vision (`backend/ai.py`)
`describe_image(image_b64, mime)` — base64 data-URL в content-массив (`text` + `image_url`), ротация по VISION_MODELS. Важно: старые модели (`qwen2.5-vl-7b:free`, `llama-3.2-11b-vision:free`, `gemma-3-27b:free`) **404 в актуальном каталоге** — список актуализирован по `GET /api/v1/models` (filter `:free` + `input_modalities` содержит image): `google/gemma-4-26b-a4b-it:free`, `google/gemma-4-31b-it:free`, `nvidia/nemotron-nano-12b-v2-vl:free`.

### 38.5. Рефакторинг `chat.py`
Логика ответа куратора (история → контекст заметок/снов/целей → `chat_with_context` → [NOTE] → [SAVE] → вставка ответа) вынесена из `ai_chat` в общий `_chat_reply(db, user_id, thread_id, project_id, request_message, background, goal_id)`. `ai_chat` и `chat_upload` теперь только готовят ветку и вставляют user-сообщение, затем вызывают хелпер — поведение идентично, `goal_id` (обсудить цель) сохранён. Это исключает дрейф между текстовым и файловым путём.

### 38.6. Хранение
Бинарный файл не хранится. В `chat_history` идёт user-сообщение `файл: <имя>\n\n<извлечённый текст или описание>`, далее обычный ответ куратора. Смысл доступен в истории ветки, поиске и бэкапе. Фоновый `_title_thread` тоже от содержимого файла (через текст user-сообщения).

### 38.7. Фронт

## 39. 18.08.2026 — Утечка reasoning-модели в ответы чата: фильтр `_is_reasoning_noise` усилен

### 39.1. Симптом
Куратор отвечал длинным англоязычным текстом: «The user wants me to write in Russian. Let me identify which notes from today (2026-08-18) are relevant to the media platform project, and then save them…». Это был chain-of-thought модели, утекший в поле `content`, а не ответ пользователю.

### 39.2. Корень
- Первая модель в `ZEN_MODELS` — `deepseek-v4-flash-free` — отдаёт свой внутренний реазинг **прямо в `content`** (не в отдельное поле `reasoning`).
- `_request_model` (ai.py) брал `content` как есть, поле `reasoning` не читал и не сверял.
- Фильтр `_is_reasoning_noise` ловил только 4 паттерна: `here's a thinking process`, `i'll think`, `let me think`, `i need to`. Реальные утечки («The user wants me…», «Let me identify…», «Based on my analysis…») не подпадали ни под один → принимались как ответ.
- Системный промпт требует ответ по-русски, а reasoning у модели идёт по-английски и в первом лице — это устойчивый признак утечки.

### 39.3. Решение
- **`_REASONING_STARTS`** — кортеж ~50 типичных начал утечки («the user wants me», «let me identify/check/look/search/find/review/analyze», «based on my», «i should/will», «first, let me», «to answer this», «from my analysis», «we need to» и т.п.). `_is_reasoning_noise` проверяет первые 120 символов.
- **`_request_model`**: отдельное поле `message.reasoning` читается; если `content` начинается с него — ответ отбрасывается (лог `reasoning-in-content`).
- Отброшенный ответ = None → ротация пробует следующую модель (механизм был в `call_ai_json`/`call_ai`/`chat_with_context`).

### 39.4. Проверка
- `python -m py_compile backend/ai.py` — OK.
- `ruff check backend/ai.py` — all checks passed.
- Прод: `/api/health` — 200; главная отдаёт `app.js?v=25`/`chat.css?v=12`; автодеплой Render подхватил push `2f34bdb`. Корневой запрос к Render free может долго открываться (cold-start) — не дефект деплоя.

### 39.5. Замечания
- Фильтр завязан на английские first-person-формулировки; если утечки вернутся в другой форме (по-русски, от третьего лица) — список расширять по образцу.
- Резервная защита: сравнение `content` с полем `reasoning` работает для API, которые отдают его отдельно (Zen/OpenRouter). Для моделей, льющих reasoning прямо в content без поля, работает только префикс-фильтр.

## 40. 18.08.2026 — Куратор раскладывает заметки по проектам (`[ASSIGN:]`)

### 40.1. Проблема
Привязка заметки к проекту (ADR-0013) существовала только в UI — кнопка «в проект» на заметке (`PUT /api/notes/{id}`). Чат-куратор про проекты не знал: список проектов не попадал в контекст, механизма привязки существующих заметок не было. Пользователь хочет задание «разложи заметки по проектам» — тонко, не скопом.

### 40.2. Подход
Продолжение линии маркеров-действий [SAVE:] (ADR-0012) и [NOTE:] (ADR): системный промпт + маркер, который парсит бэкенд. Ключевая развилка — «не всё скопом»: у куратора нет инструментального вызова, есть только маркер, поэтому тонкость зашита в инструкцию (привязывай только при явном совпадении) и в пакет контекста (только незакреплённые заметки, кратко, а не полными текстами — экономия токенов).

### 40.3. Решение
- **Интент** `_has_assign_intent`: глаголы-просьбы + негативные маркеры-вопросы («как бы», «можно ли», «что если», «предложи»). Маркер `[ASSIGN:...]` применяется только при явной просьбе, иначе вырезается (та же защита, что у [SAVE:]).
- **Контекст**: список проектов всегда в system (`_projects_context_block`); при интенте — пакет до 50 заметок без проекта (`_assign_pool_block`, id + дата + суммари/заголовок/категория, иначе первые 180 символов — классификации хватает, токенов тратится мало).
- **Маркер**: `[ASSIGN:{"<id_заметки>": <id_проекта> | "<имя>", ...}]`. Число = существующий проект, строка = имя нового (ищется по точному имени без регистра, иначе создаётся). Применяется сразу, сводка `assigned` в ответе — фронт рисует «куратор разложила по проектам: N → «Имя»…».
- **JSON-маркер в тексте**: регекс `\[ASSIGN:(\{.*?\})\].*?` с DOTALL — переживает переносы строк. План из нескольких маркеров сливается (finditer + merge). Битый JSON → игнорируется.

### 40.4. Проверка
- `test_assign_intent.py` (юнит, без сети: интент 17 кейсов + парсинг 8) — PASSED 25/25.
- `test_save_intent.py` — PASSED 16/16 (регрессии нет).
- `python -m py_compile backend/routes/chat.py backend/ai.py` — OK.
- `ruff check` — all checks passed.

### 40.5. Замечания
- Объём по умолчанию — только последние ~50 незакреплённых. «Продолжи разложить» → следующий пакет. Если нужно всё сразу — расширять `_assign_pool_block`/итерации.
- Сводка «N заметок → проект» приходит по факту применения; отката нет (решение пользователя: сразу).
- Новые проекты из чата создаются по имени из маркера — надо следить, чтобы free-модели не плодили мусорные проекты; при ложных срабатываниях добавить порог (например, минимум 2 заметки на новую тему).

## 42. 18.08.2026 — Настоящая причина «не распределяет»: утечка reasoning-простыни, фильтр не поймал

### 42.1. Симптом

Остальные паттерны простыни («I need to follow», «Let's scan», «Let's categorize», «First, I need to look») были в начале не первыми.

### 42.3. Исправление (коммит TBD)

- «i need to follow», «i have to», «my task here is», «my job is», «i'm reading/looking at/reviewing», «i've been»;
- «let's scan/categorize/group/assign/sort/begin/proceed/go», «first i need», «going through the», «stepping through».

Заодно зафиксированы примеры в `test_assign_intent.py` (блок REASONING_CASES): 9 реальных начал простыни (включая точную первую строку из ответа Марине) + 4 легитимных русских ответа Куратора, которые не должны отсекаться.

### 42.5. Замечания
- Урок из §39.2 повторился: **free-модели массово льют reasoning в `content`**, формализм начала ответа постоянно обходит фильтр. Список придётся доращивать по мере встречи новых формулировок — REASONING_CASES в тесте теперь страхует от регрессии уже известных.
